# todo-footer — расширение observability для Pi Agent

> **Pi Agent extension — a transparent todo widget that cross-checks the model's declared plan against actual tool activity.**

Липкий виджет над редактором, который делает активность агента **понятной** для
пользователя. В отличие от классического to-do, он **не** пытается контролировать
или останавливать агента — он показывает два честно подписанных канала: что агент
*реально делает* (факт) и что он *заявляет* (намерение), и помечает случай, когда
заявлена работа, а tool-активности нет.

> **Кратко, отличие от классического todo:** классический todo хранит план модели и
> доверяет ему. Это расширение считает план модели *утверждением*, показывает его
> рядом с реальными событиями инструментов харнеса и никогда не притворяется, что
> обеспечивает контроль, которого не может обеспечить.

---

## Концепция

### Проблема «контрольных» расширений

Естественный дизайн план-виджета — *ставить агента на паузу* после каждого шага и
просить пользователя подтвердить продолжение («Step mode»). Это расширение раньше
работало так. Больше не работает — и причина структурная, а не баг:

- В Pi единственный **принудительный** механизм контроля — перехват вызова инструмента
  и возврат `{ block: true }`. Всё остальное — просьба, которую модель волна игнорировать.
- Общий шаг плана («отрефакторить auth», «написать тесты») нельзя сопоставить whitelist
  разрешённых инструментов, поэтому *нельзя принудить* модель делать заявленный шаг.
- «Шлюз подтверждения» на основе `terminate: true` + произвольного текстового сообщения
  `"continue"` — **бутафория**: модель сама решает, вызывать ли шлюз, и сама
  интерпретирует сообщение возобновления. «Нет» может быть прочитано как «он не согласен,
  но я продолжу».

Так что контрольный план-виджет претендует на надзор, который не может доставить. Это
расширение выбирает противоположное: **доставлять то, что может — видимость — и быть
честным насчёт того, чего не может.**

### Два канала, честно подписанные

| Канал | Источник | Доверие | Подпись |
|---|---|---|---|
| **ФАКТ** (hard) | события харнеса `tool_execution_start` / `tool_execution_end` / `turn_start` / `turn_end` | абсолютное — харнес знает, какие инструменты запускались, независимо от честности модели | `👁 Fact` |
| **НАМЕРЕНИЕ** (soft) | модель декларирует план через инструмент `update_plan` | модель может устареть или ошибаться | `🗣 Plan (declared by model)` |

Канал факта — **ground truth**. Канал намерения — **утверждение** модели. Виджет
никогда их не смешивает.

### Проверка расхождения

Когда модель декларирует шаг `in_progress`, расширение проверяет канал факта на
наличие вообще какой-либо tool-активности — либо текущего действия
(`tool_execution_start` без парного `end`), либо любой записи в списке недавних
действий. Если **оба пусты**, виджет показывает:

```
⚠ step declared but no tool activity
```

Ловится редкий, но осмысленный случай: модель объявила работу, но буквально ничего
не делает. Проверка намеренно консервативная — она не пытается сопоставлять
*содержимое* шага с *содержимым* действий (см. *Известные ограничения*).

### Известные ограничения

- **Токен-матчинг между текстом шага и реальной активностью ненадёжен.** Словарь
  цели шага (напр. «отрефакторить auth») и словарь путей/команд (напр. `edit auth.ts`)
  принципиально не пересекаются. Ранняя версия токенизировала оба и помечала
  расхождения — это давало постоянные ложные срабатывания и было удалено. Теперь
  расширение помечает только тривиальный случай: заявлена работа, а tool-активности
  **ноль**.
- **Soft-канал зависит от сотрудничества модели.** В Pi нет способа *принудить* модель
  вызвать `update_plan`. `promptGuidelines` + per-turn напоминание `before_agent_start`
  существенно повышают частоту вызова, но не гарантируют его. На коротких задачах
  модель всё ещё часто пропускает декларацию плана. Это фундаментальный лимит
  soft-канала, а не баг.

### Детекторы аномалий (объективные, из фактов харнеса)

Три детектора подсвечивают паттерны, которые пользователь иначе пропустил бы. Все
выводятся из фактов харнеса — без угадываний о том, *что* делает модель, только подсчёт
того, *что произошло*. Виджет констатирует факт; решение за пользователем.

- **Детектор цикла.** Одинаковый вызов (то же имя + хэш аргументов) повторяется ≥3 раза
  в скользящем окне из 16 сигнатур → `⚠ loop: repeated identical calls (×N: tool)`.
  Ловит модель, переотправляющую идентичные edit/вызовы. Хэширование хранит только
  число на вызов, так что даже гигантские `edit`-параметры не стоят памяти. Alert
  сбрасывается, как только приходит не-повторяющийся вызов.
- **Серия ошибок.** ≥3 ошибки подряд → `⚠ error streak: N in a row`. Ловит модель,
  застрявшую в failing-цикле.
- **Давление контекста.** Заполнение контекста ≥30% → `⚠ context N%` (жёлтый 30–60%,
  красный >60%). Кумулятивная стоимость токенов растёт суперлинейно за ход, поэтому
  процент подсвечивается рано. Никакое действие не предлагается; пользователь решает
  сам (напр. `/compact` — план сохранится через `restoreIntent` — или новая сессия).

Каждый детектор также дёргает однократное всплывающее уведомление `ctx.ui.notify`
**в момент перехода** в аномалию (норма → аномалия), а не каждый ход, пока она длится —
так вы заметите даже не глядя на футер.

## Отличия от классического todo-виджета

| | Классический todo | todo-footer (это расширение) |
|---|---|---|
| Главная цель | отслеживать план модели | делать активность модели понятной |
| Источник истины | декларации модели | события инструментов харнеса (факт) + декларации модели (намерение, подписано) |
| Показывает, что модель делает *прямо сейчас* | редко — только если модель обновит статус | всегда — из `tool_execution_start` |
| Помечает расхождение плана и реальности | нет | да (консервативно: ноль активности на заявленном шаге) + детекторы цикла / серии ошибок / давления контекста |
| Пытается ставить шаги на паузу/одобрение | часто | **никогда** — нет `terminate`, нет шлюза одобрения, нет step mode |
| Зависит от честности модели для своей ценности | да | только для канала намерения; канал факта независим |
| Риск deadlock / зависшего состояния | высокий (одобрение может зависнуть) | нет — ничего не блокируется |

## Функционал

### Инструмент `update_plan` (вызывается моделью)

Декларирует план задач для видимости пользователя. **Только декларация — не ставит на
паузу и не контролирует выполнение.** Два complementary-механизма удерживают
инструмент «в уме» у модели:

1. **`promptGuidelines`** — буллет, добавляемый в секцию `Guidelines` системного промпта
   каждый ход, пока инструмент активен.
2. **`before_agent_start` хук** — явный блок-напоминание, инъектируемый в системный
   промпт каждый ход (сильнее, чем один общий буллет; но не enforcement).

Вместе они повышают частоту, с которой модель реально декларирует план для
многошаговой работы и обновляет статусы. Ни один из них не может *принудить* к вызову
(см. *Известные ограничения*).

Параметры:
- `tasks` — массив (0–12) из `{ text: string, status: "pending" | "in_progress" | "done" }`

Состояние сохраняется в `toolResult.details.tasks` для корректного восстановления при
branching на resume.

### Канал факта (автоматически, из событий харнеса)

Расширение подписывается на события харнеса и выводит, **без участия модели**:

- **`turn_start`** — увеличивает счётчик ходов.
- **`turn_end`** — раз за ход читает `ctx.getContextUsage()` для детектора давления контекста.
- **`tool_execution_start`** — устанавливает «now: <инструмент> <сводка>» (напр. `bash git diff`, `read auth.ts`).
- **`tool_execution_end`** — записывает действие в скользящий список «recent:» (последние 8, показывает 4) и увеличивает счётчик ошибок при `isError`. Также питаёт детектор цикла и счётчик серии ошибок. Ошибки в строке «recent:» рисуются полностью красными (не только значок).

Вызовы `update_plan` намеренно исключены из канала факта — декларация плана это намерение,
не работа; иначе «что делает модель» загрязнялось бы.

Сводки по инструментам:
- `bash` → первая строка команды (обрезается до 60 символов)
- `read` / `write` / `edit` → путь
- `grep` → pattern или путь
- `find` / `ls` → путь
- прочие → путь, иначе команда, иначе первый строковый аргумент

### Канал намерения (декларируется моделью)

План модели, восстанавливаемый из `toolResult.details.tasks` на `session_start` и
`session_compact`. Отображается под `🗣 Plan (declared by model)` с заголовком
`[done/total] pct%`, иконками статусов (`✓` done / `→` in_progress / `○` pending) и
overflow-folding для планов длиннее 7 пунктов (последние 2 done + in_progress + pending,
со строкой-сводкой «… N done hidden»).

### Команда `/todo` (пользовательская)

| Команда | Действие |
|---|---|
| `/todo` | Показать статус: число задач, ход, состояние виджета и **активные аномалии** (контекст %, цикл, серия ошибок) для быстрой триаж-оценки. **Не** переключает режим. |
| `/todo clear` | Очистить декларированный план |
| `/todo toggle` | Показать / скрыть виджет |

Нет `/todo mode` и нет шорткатов `A`/`S`/`C` — они принадлежали удалённому контрольному слою.

### Раскладка виджета

```
👁 Fact · turn 4
  now: read auth.ts
  recent:  · bash git status   · read config.ts   ✓ edit auth.ts
  ⚠ session errors: 1
  ⚠ context 34%
────────────────────────────────────────
🗣 Plan (declared by model) [2/5] 40%
  ✓ 1. Study the auth module
  → 2. Fix the logout bug
  ○ 3. Add tests
  ⚠ step declared but no tool activity
```

Три строки аномалий (`context`, `loop`, `error streak`) — условные, появляются только
пока активен соответствующий детектор. В спокойной сессии блок факта — это просто
header + `now:`/`recent:` + счётчик ошибок сессии.

- Каждая строка обрезается до ширины терминала через `truncateToWidth` (контракт TUI).
- Разделитель и секция намерения появляются только когда план декларирован.
- Строка расхождения появляется только когда срабатывает консервативная проверка
  (заявлен `in_progress`-шаг с нулём tool-активности).

> Пояснения в этом README — на русском.

## Установка

Скопируйте `todo-footer.ts` в глобальный каталог расширений:

```bash
mkdir -p ~/.pi/agent/extensions/
cp todo-footer.ts ~/.pi/agent/extensions/
```

Или в project-local расширения (загружается только для доверенного проекта):

```bash
mkdir -p .pi/extensions/
cp todo-footer.ts .pi/extensions/
```

Расширение загрузится автоматически при следующей сессии Pi. Чтобы применить без
перезапуска — выполните `/reload` в работающей сессии.

## Архитектура

```
todo-footer.ts
├── Types & Schema          — Task, TaskStatus, FactAction; TypeBox-валидация
├── Constants               — MAX_RECENT_ACTIONS, MAX_VISIBLE_TASKS, пороги аномалий
├── Helpers (чистые)
│   ├── countByStatus, summarizeToolCall
│   ├── hashString, callSignature — djb2-хэш + стабильная сигнатура вызова для детектора цикла
│   └── (хелперы токен-матчинга удалены — см. Известные ограничения)
├── Extension (closure)
│   ├── State               — declaredTasks (намерение), currentAction/recentActions/turnCount/errorsThisSession (факт),
│   │                         состояние аномалий (recentSignatures/loopAlert/consecutiveErrors/lastContextPercent + was*-флаги переходов), widgetVisible
│   ├── normalizeTasks      — валидация + trim за один проход (схема уже проверяет форму)
│   ├── restoreIntent       — сканирует ветку на последний details.tasks от update_plan (для /resume)
│   ├── Rendering           — buildFactLines (вкл. строки аномалий), buildIntentLines, buildWidgetLines (все учитывают width)
│   ├── updateWidget        — factory-форма setWidget(key, (tui,theme) => Component), render(width)
│   ├── update_plan tool    — только декларация; promptGuidelines + before_agent_start держат в уме; без terminate
│   ├── /todo command       — clear / toggle / status-со-сводкой-аномалий (без переключения режима)
│   ├── FACT events         — turn_start, turn_end (чтение контекста), tool_execution_start/end (update_plan исключён)
│   ├── Anomaly detectors   — loop (окно сигнатур), error streak (подряд), context pressure (getContextUsage); notify на переходе
│   ├── before_agent_start hook — per-turn явное напоминание, инъектируемое в системный промпт (усиление soft-канала)
│   └── Lifecycle           — session_start (сброс фактов + состояния аномалий, restore намерения), session_compact (восстановление намерения), session_shutdown (очистка)
```

### Ключевые design-решения

- **Нет контрольного слоя.** Нет `terminate`, нет шлюза одобрения, нет step mode.
  Расширение доставляет видимость, а не надзор, который не может обеспечить. (См. *Концепцию*.)
- **Факт эфемерен, намерение сохраняется.** Состояние факта сбрасывается на `session_start`
  (его нельзя правдиво восстановить из истории); намерение восстанавливается из
  `details.tasks` для корректного branching.
- **`update_plan` исключён из канала факта**, чтобы «что делает модель» отражало реальную
  работу (`bash`/`read`/`edit`/…), а не декларации плана.
- **`promptGuidelines` + per-turn напоминание `before_agent_start`.** Прежняя
  контрольная версия делала разовую инъекцию напоминания через `before_agent_start`
  с флагом `instructionAdded`, которая забывалась после первого хода. Observability-версия
  использует **оба** механизма, оба per-turn: `promptGuidelines` держит буллет в списке
  `Guidelines`, пока инструмент активен, а хук `before_agent_start` добавляет короткий
  явный блок-напоминание в системный промпт каждый ход — более сильный nudge, чем один
  общий буллет. Флаг `instructionAdded` намеренно отсутствует: системный промпт
  пересобирается каждый ход, так что ре-инъекция каждый ход корректна. Это всё ещё
  **не** enforcement — модель может проигнорировать (см. *Известные ограничения*).
- **Рендеринг с учётом ширины.** Виджет использует factory-форму и обрезает каждую строку
  до `width`, удовлетворяя контракту TUI `render(width)` (длинные пути/команды больше не
  ломают вёрстку).
- **Без внешних зависимостей** — импортирует только из рантайма Pi (`pi-coding-agent`,
  `pi-tui`, `pi-ai`, `typebox`).
- **Детекторы аномалий — чистое наблюдение, не контроль.** Они подсчитывают факты харнеса
  (сигнатуры вызовов, подряд идущие ошибки, % контекста) и подсвечивают их — плюс
  однократный тост на переходе норма→аномалия. Они никогда не прерывают модель, никогда
  не авто-компактят, не совершают никаких действий над сессией. Эта граница (читать
  факты и сообщать vs. воздействовать на сессию) — граница философии расширения.

## Скрипты dev-цикла

Два шелл-скрипта (в репозитории проекта, не в расширении) превращают цикл
редактирование-проверка-деплой в одну команду:

| Скрипт | Действие |
|---|---|
| `./check.sh` | `tsc --strict` против глобально установленного пакета Pi (подставляет саб-зависимости через временный tsconfig). Ненулевой exit при любой ошибке. |
| `./deploy.sh` | Сначала гоняет `check.sh` (пропустить через `--no-check`), потом копирует `todo-footer.ts` в `~/.pi/agent/extensions/` и напоминает сделать `/reload`. |

Они живут вне расширения намеренно — комманда `/todo deploy` запускалась бы из
*уже установленной* копии, пока ты правишь исходник, ловушка курицы-яйца. Отдельный
скрипт не имеет такой зависимости.
